# Photo Chooser — SPEC

- **Статус:** Draft, на ревью. Версия 0.1 реализована; изменения версии 0.2 — роли ленты и stories (FR-3 п.8, D8), стиль страницы Instagram (FR-11, D9)
- **Дата:** 2026-11-01
- **Платформа:** macOS 26 (Tahoe), Apple Silicon

## 1. Проблема

После путешествий остаётся очень много фотографий. Отбирать их вручную тяжело, процесс затягивается и сходит на нет, а Instagram (лента и stories) так и не ведётся.

## 2. Цель

CLI-приложение для macOS, которое по альбому из Photos и заданным темам формирует **шорт-лист** лучших кадров, разложенный на кандидатов для **ленты** и для **stories**. Финальный выбор делает пользователь. Отобранные кадры дальше обрабатываются в другом инструменте.

Приоритеты при компромиссах: **качество отбора > время > цена**.

## 3. Сценарий использования

1. После поездки пользователь собирает фото поездки в альбом в Photos (~1000 фото).
2. Описывает темы в `trip.yaml` (или задаёт одну тему аргументами CLI): по содержанию («пирамиды, сфинкс»), по интервалу времени («14 марта, 05:00–12:00») или по обоим признакам.
3. Запускает `photo-chooser run trip.yaml` в Terminal.
4. Получает директорию с копиями оригиналов: для каждой темы `feed/` и `stories/`, файлы пронумерованы по рангу, рядом `report.md` с причинами выбора.
5. Просматривает шорт-лист в Finder, выбирает финальные кадры и обрабатывает их в своём инструменте.

## 4. Scope

**В scope (MVP):**
- CLI без GUI.
- Чтение альбома Photos через PhotoKit, включая оригиналы в iCloud («Оптимизация хранилища»).
- Фото: HEIC, JPEG, Live Photo. Снимки с RAW обрабатываются по основному файлу (FR-2.2).
- Темы по содержанию кадра (текстовый запрос на любом языке) и/или по интервалу времени.
- Отсев мусора и дублей, двухступенчатая оценка в облаке, раскладка на ленту и stories.
- Копирование оригиналов в отдельную директорию и отчёт с короткой причиной выбора.
- Выбор моделей Claude и режим без облака для дешёвой и бесплатной отладки.
- Учёт стиля страницы Instagram автора по образцам из Photos (FR-11).

**Вне scope:**
- Обработка кадров (перспектива, горизонт, баланс белого и т. п.) — пользователь делает её сам в другом инструменте.
- Видео.
- Любая запись в Photos: альбомы, метки, правки, избранное.
- Общие (shared) альбомы.
- Отдельная поддержка RAW: копирование второй части пары RAW+JPEG/HEIC — позже.
- Публикация в Instagram, подписи, хэштеги.
- Доступ к самой странице Instagram (API, парсинг): образцы стиля берутся из Photos (FR-11).
- Распознавание автора на кадрах: такие кадры пользователь отбирает вручную.
- GUI.
- Геотеги: метка в геотеге может быть некорректной, поэтому координаты не используются ни для темы, ни для часового пояса.

## 5. Функциональные требования

### FR-1. Входные данные

- **FR-1.1.** Источник — один обычный альбом Photos, указанный по имени.
- **FR-1.2.** Тема задаётся полями:
  - `name` — имя темы, обязательно;
  - `query` — что искать в кадре, текст на любом языке;
  - `from` / `to` — интервал времени.

  Нужен хотя бы один из признаков: `query` или интервал. Если указаны оба, кадр должен удовлетворять обоим.

  Темы с `query` оцениваются на первой ступени вместе, поэтому тема может ссылаться на другие темы запуска («оставшиеся храмы»). Формулировка заметно влияет на результат: аббревиатуры и неоднозначные названия лучше расшифровывать («GEM (Большой Египетский музей)», «Карнакский храм», а не «Карнакский музей»).
- **FR-1.3.** Интервал времени трактуется в **местном времени поездки**: время съёмки снимка переводится в часовой пояс `timezone` из `trip.yaml` (в CLI-режиме — флаг `--timezone`), например `Africa/Cairo`. `timezone` обязателен, если хотя бы у одной темы задан интервал; без него запуск останавливается с ошибкой конфигурации.
- **FR-1.4.** Тема только с интервалом (например, «День 3») означает, что все кадры интервала релевантны и ранжируются только по качеству.
- **FR-1.5.** Один кадр может попасть в несколько тем одного запуска: первая ступень может отнести его к нескольким темам, а вторая ступень и раскладка выполняются по каждой теме отдельно. Внутри одной темы кадр попадает либо в ленту, либо в stories, но не в оба списка.

### FR-2. Типы медиа

- **FR-2.1.** Учитываются фото: HEIC, JPEG, Live Photo. Видео игнорируются.
- **FR-2.2.** RAW в MVP отдельно не поддерживается: у любого снимка копируется только основной файл (ресурс Photo). Для пары RAW + JPEG/HEIC вторая часть не копируется.
- **FR-2.3.** Live Photo см. FR-5.

### FR-3. Конвейер отбора

Общие для всех тем этапы (один раз на запуск; локальные признаки кэшируются по альбому):

1. **Чтение альбома** через PhotoKit (только чтение): снимки с датой, размерами и признаками Live Photo и скриншота.
2. **Превью** с длинной стороной `preview_long_side_px`. Если превью нет на Mac, PhotoKit скачивает его из iCloud. Если превью получить не удалось, снимок пропускается и учитывается в отчёте как «нет превью».
3. **Отсев мусора:**
   - скриншоты (признак PhotoKit). Флаг Apple Vision «утилитарный кадр» для отсева не используется: на альбоме поездки он помечал росписи гробниц, рельефы и музейные экспонаты, а не документы и чеки. Таблички, документы и экраны отсекают облачные ступени;
   - крайний смаз: только почти однородные кадры. Резкость не годится как общий порог: у плавных сюжетов (закат, небо, дымка, вода) она низкая без всякого смаза;
   - полностью пересвеченные или чёрные кадры.

   Порог мягкий: отсекается только явный брак, потому что stories допускают изъяны. Остальной брак оценивают облачные ступени.
4. **Дубли и серии.** Похожие кадры, снятые близко по времени, объединяются в кластер по визуальному отпечатку Vision и времени съёмки. Дальше идёт один представитель кластера — лучший по **локальной оценке качества**: эстетика Vision, резкость, качество лиц. Внутри серии сюжет одинаковый, поэтому сравнение резкости здесь честное.
5. **Первая ступень — отбор по всем темам сразу** (модель `screen_model`, по умолчанию `claude-haiku-5-5`, один проход на запуск). Все оставшиеся снимки отправляются группами; в каждом запросе — название альбома и пронумерованный список тем запуска с `query`. По каждому снимку возвращается:
   - темы, к которым относится кадр, с релевантностью 1–10 (10 — место или объект темы и есть содержание кадра; темы ниже 5 не указываются). Кадр может относиться к нескольким темам или ни к одной (аэропорт, самолёт, отель);
   - черновые оценки для ленты и для stories, шкала 1–10, по тем же ролям списков, что и на второй ступени (п.8), без учёта стиля страницы.

   Если в запуске нет тем с `query`, первая ступень не выполняется.

Для каждой темы:

6. **Фильтр интервала**, если он задан (FR-1.3).
7. **Кандидаты.** Тема с `query` — снимки интервала с релевантностью к теме не ниже `min_theme_relevance` (по умолчанию 5: на этой ступени полнота важнее точности, вторая ступень перепроверяет соответствие). Тема только с интервалом — все снимки интервала. Кандидаты сортируются по релевантности, затем по большей из двух черновых оценок, затем по локальной оценке качества; во вторую ступень идут первые `candidates_per_theme`.
8. **Вторая ступень — оценка** (модель `model`). Кандидаты отправляются группами вместе с описанием темы, профилем стиля и образцами страницы (FR-11). По каждому кадру возвращается:
   - соответствует ли кадр теме;
   - сила кадра для **ленты** — лучшие кадры поездки: композиция, свет, визуальное впечатление, техническое качество, соответствие стилю ленты (FR-11.4); кадры без людей часто сильнее всего именно для ленты; шкала 1–10;
   - пригодность для **stories** — «упрощённая лента» поездки: хорошие кадры по теме, которые рассказывают о поездке, в том числе не дотягивающие до ленты по качеству; люди не обязательны, небольшие технические изъяны допустимы, учитывается соответствие стилю stories (FR-11.4); шкала 1–10;
   - короткая причина на языке темы: чем кадр хорош или слаб. Отсутствие людей недостатком не считается.

   Кадры, которые модель сочла не соответствующими теме, исключаются. Для темы только с интервалом эта проверка не применяется.
9. **Раскладка** (FR-4).
10. **Live Photo** из итоговых списков обрабатываются по FR-5.
11. **Экспорт** (FR-6).

В режиме без облака этапы 5 и 8 пропускаются (FR-10.2).

### FR-4. Лента и stories

- **FR-4.1. Лента:** до `shortlist.feed` кадров (по умолчанию 20) с наибольшей оценкой «лента» второй ступени и не ниже порога `min_feed_score`. Ориентация не важна.
- **FR-4.2. Stories:** до `shortlist.stories` кадров (по умолчанию 40) из оставшихся, с оценкой «stories» второй ступени не ниже порога `min_stories_score`. Этот порог ниже порога ленты. Порядок: сначала все подходящие **вертикальные** кадры по убыванию оценки, затем горизонтальные (квадратные идут вместе с горизонтальными).
- **FR-4.3.** Если подходящих кадров меньше лимита, в шорт-лист кладётся столько, сколько нашлось. Недобор мусором не заполняется, в отчёте указывается, сколько кадров не хватило.

### FR-5. Live Photo

- **FR-5.1.** Live Photo рассматривается как короткая анимация. Кандидаты на итоговый кадр — ключевой снимок и кадры видеочасти.
- **FR-5.2.** Кадры оцениваются локально: резкость, эстетика, качество лиц (открытые глаза).
- **FR-5.3.** У ключевого снимка разрешение выше, поэтому кадр видеочасти выбирается, только если он **явно** лучше: превосходит ключевой снимок на величину `live_frame_margin` из конфига.
- **FR-5.4.** Если выбран ключевой снимок, копируется его оригинал (HEIC/JPEG). Если выбран кадр видео, он сохраняется в **TIFF** (без потерь), в него переносятся дата и геоданные из оригинала, имя файла получает суффикс `_live-frame`. В отчёте указывается, что разрешение кадра ниже оригинала.
- **FR-5.5.** Видеочасть скачивается из iCloud только для Live Photo, попавших в итоговые списки. Если скачать её не удалось, копируется оригинал ключевого снимка, в отчёте — пометка.

### FR-6. Результат

- **FR-6.1.** Каждый запуск пишет в новую директорию и ничего не перезаписывает:

  ```
  <output_dir>/<альбом>/<YYYY-MM-DD_HHMM>/
    <тема>/
      feed/01_IMG_4521.HEIC
      feed/02_IMG_4533.JPG
      stories/01_IMG_4610_live-frame.tiff
      report.md
  ```

- **FR-6.2.** Копируются **оригиналы**, без правок, сделанных в Photos. Двузначный префикс в имени — ранг внутри списка.
- **FR-6.3.** `report.md` на тему содержит:
  - шапку: модели обеих ступеней (или «без облака»), `effort`, версия промпта, профиль стиля (дата и отпечаток `style.md`, число скриншотов-образцов) или предупреждение о его отсутствии (FR-11.5) — чтобы прогоны на разных моделях можно было сравнивать;
  - таблицу: ранг, файл(ы), лента или stories, оценка, ориентация, пометки (кадр из Live Photo), короткая причина выбора;
  - сводку: сколько снимков прочитано, без превью, отсеяно как мусор, схлопнуто как дубли, прошло интервал, признано подходящими к теме на первой ступени, отправлено на вторую ступень; стоимость первой ступени (общая на запуск) и второй (по теме), накопленная стоимость по альбому; недобор по FR-4.3; пропущенные снимки с причиной.

### FR-7. CLI

```
photo-chooser albums                     # список альбомов Photos
photo-chooser run trip.yaml              # все темы из файла поездки
photo-chooser run --album "Египет 2026" --theme "Гиза" --query "пирамиды, сфинкс" \
                  [--from "2026-03-12 06:00" --to "2026-03-12 14:00"] [--timezone Africa/Cairo]
photo-chooser run ... --dry-run          # только локальные этапы + оценка стоимости
photo-chooser run ... --max-cost 8       # разово поднять лимит бюджета
photo-chooser run ... --model claude-sonnet-5-5   # модель второй ступени для этого запуска
photo-chooser run ... --no-cloud         # без Claude: только локальные оценки, бесплатно
photo-chooser style [--yes]              # построить профиль стиля страницы Instagram (FR-11)
```

`--timezone` обязателен вместе с `--from` / `--to` (FR-1.3).

- **FR-7.1.** `--dry-run` выполняет общие этапы 1–4 и фильтр интервала, выводит число снимков по темам и оценку стоимости обеих ступеней: первая — один проход по всем снимкам после отсева, вторая — `candidates_per_theme` кандидатов на тему. Режим не обращается к Claude и ничего не копирует.

### FR-8. Конфигурация

Общий конфиг `~/.config/photo-chooser/config.yaml`:

```yaml
output_dir: ~/Pictures/photo-chooser
shortlist:
  feed: 20
  stories: 40
cloud:
  screen_model: claude-haiku-5-5   # первая ступень — отбор
  model: claude-haiku-5-5          # вторая ступень; на время отладки, прод-модель фиксируется по §12
  effort: medium                   # для прод-модели подбирается по §12
  pricing:                         # $ за 1 млн токенов (вход / выход), для оценки стоимости
    claude-haiku-5-5:  {input: 0.10, output: 0.50}
    claude-sonnet-5-5: {input: 2.00, output: 10.00}
    claude-opus-5-5:   {input: 4.00, output: 20.00}
  max_cost_usd_per_album: 5.0      # лимит накопленной стоимости по альбому, обе ступени
  candidates_per_theme: 100        # сколько кадров первая ступень передаёт второй
  preview_long_side_px: 1024
  group_size: 20
thresholds:                        # значения по умолчанию — docs/spike-findings.md
  min_theme_relevance: 5           # порог релевантности первой ступени для кандидатов
  junk_blur: …
  duplicate_distance: …
  min_feed_score: …
  min_stories_score: …
  live_frame_margin: …
style:                             # стиль страницы Instagram (FR-11)
  albums: [Snapseed, Instasize]    # опубликованные посты; одноимённые альбомы берутся все
  since: 2018-01-01                # более старые снимки не берутся
  screenshots_album: Instagram style   # скриншоты гридов и подборок stories
  sample: 40                       # сколько постов отправить при построении профиля
  model: claude-opus-5-5           # модель, которая пишет профиль (разово)
  reference_images: 2              # сколько скриншотов прикладывать к запросам второй ступени
```

Файл поездки `trip.yaml`:

```yaml
album: "Египет 2026"
timezone: Africa/Cairo              # обязателен, если у какой-либо темы есть интервал
themes:
  - name: Гиза
    query: "пирамиды, сфинкс, верблюды на фоне пирамид"
  - name: Абу-Симбел
    query: "храм с колоссами Рамзеса"
    from: 2026-03-14 05:00
    to:   2026-03-14 12:00
  - name: День 3
    from: 2026-03-15 00:00
    to:   2026-03-15 23:59
```

Ключ Claude API в конфиге не хранится. Он берётся из `ANTHROPIC_API_KEY` или из профиля `ant auth login`. В режиме `--no-cloud` ключ не нужен.

### FR-9. Бюджет и кэш

- **FR-9.1.** Перед облачными этапами рассчитывается оценка стоимости обеих ступеней по всем темам запуска. Если **накопленная стоимость по альбому + оценка** превышает `max_cost_usd_per_album`, запуск останавливается до отправки чего-либо в облако и выводит оценку. Разово поднять лимит можно флагом `--max-cost`.
- **FR-9.2.** Фактическая стоимость (по `usage` ответов API) записывается в кэш и в отчёт.
- **FR-9.3.** Кэш (SQLite, `~/Library/Caches/photo-chooser/`):
  - локальные признаки хранятся по снимку (идентификатор PhotoKit);
  - оценки первой ступени — по ключу «снимок × набор тем (хэш названия альбома и списка тем с `query`) × модель × версия промпта»: изменение списка тем запускает первую ступень заново;
  - оценки второй ступени — по ключу «снимок × тема (хэш name+query+интервал) × модель × версия промпта и отпечаток профиля стиля (хэш `style.md` и выбранных скриншотов-образцов)»: правка профиля или смена скриншотов пересчитывает вторую ступень, первая остаётся в кэше.

  Повторный запуск той же темы не платит за облако повторно и продолжает работу с места сбоя.

### FR-10. Выбор модели и режим без облака

- **FR-10.1. Выбор модели.** Модель первой ступени задаётся в `cloud.screen_model`, второй — в `cloud.model`; флаг `--model` переопределяет модель второй ступени на один запуск. Поддерживаются модели Claude с приёмом изображений; проверяются `claude-haiku-5-5`, `claude-sonnet-5-5`, `claude-opus-5-5`. Если для модели нет цены в `cloud.pricing`, запуск останавливается до отправки в облако: без цены нельзя проверить бюджет (FR-9.1).
- **FR-10.2. Режим без облака** (`--no-cloud`). Обе облачные ступени пропускаются, Claude не вызывается, стоимость $0. Назначение режима — бесплатная отладка механики (чтение альбома, отсев, дубли, раскладка, экспорт, отчёт), а не качество отбора. Правила:
  - `query` игнорируется, тема фильтруется только интервалом; если интервала нет, кандидаты — все снимки после отсева. В отчёте — предупреждение;
  - лента — топ-`shortlist.feed` по локальной оценке качества;
  - stories — следующие `shortlist.stories` по локальной оценке, сначала вертикальные, затем горизонтальные;
  - пороги `min_feed_score` и `min_stories_score` не применяются: они заданы в шкале оценок модели;
  - причина в отчёте — составляющие локальной оценки (эстетика, резкость, лица).
- **FR-10.3. Отладка** идёт на `claude-haiku-5-5` для обеих ступеней и в режиме без облака.
- **FR-10.4. Выбор прод-модели второй ступени** — прогоны одних и тех же тем на разных моделях с ручным сравнением `report.md` (§12). Кэш разделяет оценки по модели (FR-9.3), каждый прогон пишет в свою директорию (FR-6.1), поэтому прогоны не смешиваются. Сравнительные прогоны расходуют общий лимит альбома; при необходимости он поднимается флагом `--max-cost`.

### FR-11. Стиль страницы Instagram

- **FR-11.1. Образцы.** Опубликованные посты — снимки из альбомов Photos `style.albums` (одноимённые альбомы берутся все, повторы снимков между альбомами убираются), снятые не раньше `style.since`. Скриншоты страницы — гриды ленты и подборки stories — из альбома `style.screenshots_album`. К самой странице Instagram программа не обращается.
- **FR-11.2. Построение профиля** — команда `photo-chooser style`:
  - выбирает `style.sample` постов: чем новее снимок, тем чаще он попадает в выборку (примерно половина выборки — из самой новой четверти снимков, дальше реже, вплоть до `style.since`);
  - добавляет скриншоты страницы, не больше 12;
  - отправляет их одним запросом модели `style.model`; каждый образец подписан типом («пост» или «скриншот страницы») и месяцем съёмки;
  - модель пишет описание стиля на русском, около 300 слов, с разделами «Лента» и «Stories»: обработка, свет и цвет, композиция, типичные сюжеты, чего на странице не бывает; свежие посты весомее старых;
  - перед отправкой выводит число изображений и оценку стоимости и ждёт подтверждения; флаг `--yes` подтверждает заранее;
  - если постов-образцов меньше 10, останавливается с сообщением.
- **FR-11.3. Профиль** сохраняется в `~/.config/photo-chooser/style.md`, прежний переименовывается в `style.prev.md`. Файл можно читать и править руками.
- **FR-11.4. Использование** — только на второй ступени (FR-3 п.8). В каждый запрос добавляются текст профиля и первые `style.reference_images` скриншотов из `style.screenshots_album` в порядке альбома (порядок задаёт пользователь в Photos), с длинной стороной 1568 px, помеченные как образцы страницы, которые не оцениваются. Соответствие стилю — один из критериев оценок ленты и stories, по важности наравне с композицией и светом; вес калибруется по результатам прогонов (§12).
- **FR-11.5. Без профиля** — если `style.md` нет, вторая ступень идёт без стиля, в шапке отчёта предупреждение «Профиль стиля не найден — выполните `photo-chooser style`». В режиме `--no-cloud` стиль не используется.
- **FR-11.6. Стоимость.** Расход команды `style` записывается в кэш расходов отдельно от бюджета альбома (FR-9.1). Скриншоты-образцы и текст профиля входят в оценку стоимости второй ступени и в проверку ценового порога группы.

|---|---|---|

| NFR-2 | Стоимость облачной части (обе ступени) на альбом ~1000 фото ≤ $5 | Защита бюджета (FR-9.1) и фактическая стоимость в отчёте |
| NFR-3 | Качество: в топ-20 ленты ≥ 10 кадров, которые пользователь готов обработать и опубликовать; в 40 stories ≥ 20 пригодных | Ручная оценка пользователем на альбоме прошлой поездки |
| NFR-4 | Первый прогон альбома ~1000 фото ≤ 30 мин; повторный прогон той же темы ≤ 5 мин | Замер на альбоме прошлой поездки |

## 7. Архитектура

**Стек:** Python 3.12; доступ к Photos через PhotoKit (`pyobjc-framework-Photos`); Apple Vision и AVFoundation через `pyobjc`; Claude API через официальный Python SDK `anthropic`.

**Модули** (пакет `photo_chooser`). Внешние системы спрятаны за интерфейсами:

| Модуль | Ответственность |
|---|---|
| `library` | Доступ к Photos **только на чтение** через PhotoKit: список альбомов, снимки альбома (идентификатор, имя файла, дата, тип: Live Photo/скриншот, размеры), превью, экспорт оригинала и видеочасти Live Photo с загрузкой из iCloud. Интерфейс позволяет заменить реализацию Swift-хелпером |
| `vision` | Обёртки над Apple Vision: эстетическая оценка, визуальный отпечаток, качество лиц |
| `analysis` | Отсев мусора, кластеры дублей, локальная оценка качества, выбор кадра Live Photo |
| `judge` | Claude: обе ступени (отбор и оценка) — группы, запрос со структурированным ответом (JSON-схема), оценка стоимости, защита бюджета |
| `style` | Профиль стиля страницы: выбор образцов из Photos, запрос к Claude, `style.md`, отпечаток профиля для ключа кэша, скриншоты-образцы для второй ступени (FR-11) |
| `select` | Чистая логика раскладки на ленту и stories: по оценкам второй ступени (FR-4) или по локальным оценкам в режиме без облака (FR-10.2) |
| `export` | Копирование оригиналов, сохранение кадра Live Photo в TIFF с метаданными, `report.md` |
| `cache` | SQLite-кэш признаков, оценок и учёта стоимости |
| `config` / `cli` | Загрузка и валидация `config.yaml` / `trip.yaml`, команды CLI |

**Поток данных:**

```
альбом → снимки + превью → [мусор] → [кластеры дублей] → признаки (кэш)
  └─ для каждой темы: [интервал] → 1-я ступень: отбор (кэш) → топ-N
       → 2-я ступень: оценка (кэш) → select → Live Photo → export + report.md
```

## 8. Внешние ограничения

- macOS 26 (Tahoe), Apple Silicon.
- Медиатека Photos с включённой «Оптимизацией хранилища»: оригиналы лежат в iCloud и скачиваются по требованию.
- Terminal, из которого запускается приложение, один раз получает доступ **Photos** (запрос macOS при первом обращении). Full Disk Access не нужен. Приложение проверяет доступ и подсказывает, что сделать.
- PhotoKit не отдаёт часовой пояс снимка и оценки качества, которые считает сам Photos. Пояс определяется по FR-1.3, оценки Photos не используются.
- Видеочасть Live Photo имеет заметно меньшее разрешение, чем ключевой снимок.
- Для облачных ступеней нужен ключ Claude API, использование платное.
- На первой ступени в Claude API уходят превью почти всех снимков альбома (после отсева мусора и дублей); на второй — превью кандидатов.

## 9. Интеграции

### Photos (PhotoKit через pyobjc)

- Альбом — по имени среди обычных альбомов пользователя.
- Снимки: дата создания, размеры, признаки Live Photo и скриншота, ресурсы снимка (основное фото, видеочасть Live Photo).
- Превью — через менеджер изображений PhotoKit с разрешением загрузки из iCloud.
- Оригиналы и видеочасть — запись ресурсов в файл с разрешением загрузки из iCloud.
- Побочный эффект загрузки: Photos может временно хранить скачанные файлы на Mac. Содержимое медиатеки (правки, альбомы, метаданные) при этом не меняется.
- Ошибка загрузки обрабатывается так: повтор до 3 раз, затем снимок пропускается, на его место встаёт следующий кандидат, в отчёт записывается причина.

### Apple Vision / AVFoundation (через pyobjc)

- Vision даёт эстетическую оценку, визуальный отпечаток для поиска дублей и качество лиц.
- AVFoundation извлекает кадры видеочасти Live Photo.

### Claude API

- **Модели:** первая ступень — `cloud.screen_model`, вторая — `cloud.model` или флаг `--model` (FR-10). Отладка — `claude-haiku-5-5` на обеих ступенях, прод-модель второй ступени выбирается по §12.
- **Вход:** превью кадров с длинной стороной `preview_long_side_px` (по умолчанию 1024), группы по `group_size` (по умолчанию 20). Первая ступень — с названием альбома и списком всех тем с `query`; вторая — с описанием одной темы, общей рубрикой оценки, текстом профиля стиля и скриншотами-образцами страницы с длинной стороной 1568 px (FR-11.4). Построение профиля — один запрос с ~50 образцами (FR-11.2). На второй ступени кандидаты распределяются по группам так, чтобы в каждой был разброс черновых оценок.
- **Выход:** структурированный JSON по схеме. Первая ступень: `id`, `matches` (номер темы + релевантность 1–10), `feed_score`, `stories_score`. Вторая: `id`, `matches_theme`, `feed_score`, `stories_score`, `reason`.
- **Оценка стоимости:** перед отправкой, по формуле токенов на превью (≈ ширина × высота / 750; в spike — ~1015 токенов на превью 1024 px).
- **Лимит скорости:** у организации пользователя 500 000 входных токенов в минуту на Haiku 5.5. Запросы идут с ограничением параллельности и ожиданием при ответе 429; первая ступень по ~1000 снимкам занимает не меньше ~2 минут.
- **Ошибки:**
  - повторы средствами SDK;
  - обработка `stop_reason: refusal`;
  - если тема всё равно не обработана, остальные темы продолжаются, а отчёт её помечает.
- **Ориентир стоимости** (по замерам spike): первая ступень на Haiku 5.5 — ~$0.15 на 1000 снимков после отсева, **один раз на запуск** независимо от числа тем. Вторая ступень по ~100 кандидатам на тему:

  | Модель второй ступени | ≈ за тему | Тем в лимит $5 (с первой ступенью) |
  |---|---|---|
  | `claude-haiku-5-5` | ~$0.02 | больше 100 |
  | `claude-sonnet-5-5` | ~$0.3–0.4 | ~12 |
  | `claude-opus-5-5` | ~$0.7–1.0 | 5–6 |

  Цена Haiku 5.5 действует для запросов до 100K токенов; запрос с группой из 20 превью и двумя скриншотами-образцами укладывается в этот предел.

  Стиль страницы (FR-11): построение профиля на `claude-opus-5-5` — ≈ $0.25 разово; скриншоты-образцы и профиль добавляют ~4 тыс. входных токенов на группу второй ступени (на Opus 5.5 ≈ +$0.07 на тему из 100 кандидатов, на Haiku — пренебрежимо).

## 10. Тестирование

- **Юнит-тесты (pytest)**, Photos и Claude заменены заглушками:
  - валидация конфигов и тем;
  - перевод времени съёмки в пояс поездки, интервалы, обязательность `timezone` при интервалах;
  - кластеризация дублей на синтетических векторах;
  - обе ступени: группы, отбор кандидатов, обработка пропусков и refusal;
  - правила раскладки (FR-4): пороги, порядок вертикальные → горизонтальные, недобор;
  - нумерация и имена файлов, суффикс `_live-frame`;
  - генерация `report.md`;
  - защита бюджета и кэш;
  - выбор модели и остановка для модели без цены в `pricing`; режим без облака (FR-10.2);
  - стиль (FR-11): выбор образцов (давность, повторы между альбомами, минимум постов), запрос построения профиля и запись `style.md`, профиль и скриншоты в запросе второй ступени, ключ кэша по отпечатку профиля, работа без профиля.
- **Интеграционный тест** на тестовом альбоме Photos (~30 фото). Альбом содержит известные случаи: серию дублей, скриншот, смазанный кадр, Live Photo, кадры двух разных «тем». Тест проверяет FR-3–FR-6, NFR-1 и NFR-5.
- **Оценка качества** (NFR-3, NFR-4) — прогон на альбоме прошлой поездки с ручной оценкой пользователя.

## 11. Первый шаг реализации — spike

Цель — проверить предпосылки до основной разработки. Скрипт, обращающийся к Photos, запускает пользователь в своём Terminal (с доступом только к Photos); остальные проверки выполняются по скопированным файлам. На медиатеке пользователя (macOS 26, «Оптимизация хранилища») проверить:

1. PhotoKit через pyobjc из Terminal получает доступ Photos, находит альбом по имени и отдаёт по снимкам: дату, размеры, признаки Live/скриншот, ресурсы (основное фото, видеочасть).
2. Превью снимков, оригиналы которых в iCloud, получаются через PhotoKit; время на 1000 снимков.
3. Скачиваются из iCloud и записываются в файлы оригиналы и видеочасть Live Photo.
4. Через `pyobjc` работают эстетическая оценка Vision и визуальный отпечаток; подбираются пороги отсева мусора и дублей.
5. Первая ступень на `claude-haiku-5-5` по 5 запросам пользователя: полнота и точность отбора на ~200 превью, расход токенов и время на тему.
6. По результатам выбираются значения по умолчанию `candidates_per_theme`, `preview_long_side_px`, `group_size`.

**Критерий провала:** не выполняется пункт 1 или 3. Тогда модуль `library` переводится на Swift-хелпер с PhotoKit (решение D1), остальное не меняется.

## 12. Выбор прод-модели

Выполняется после отладки, когда конвейер и промпты стабилизированы на `claude-haiku-5-5` и в режиме без облака. Выбирается модель **второй** ступени; первая остаётся на Haiku 5.5, если прогоны не покажут, что она пропускает подходящие кадры.

1. Взять альбом прошлой поездки и 2–3 темы разного типа: по содержанию, по интервалу, смешанную.
2. Прогнать их с кандидатами в прод-модели второй ступени: `claude-haiku-5-5`, `claude-sonnet-5-5`, `claude-opus-5-5`.
3. Пользователь сравнивает `report.md` прогонов по качеству (NFR-3) и стоимости (NFR-2). Время (NFR-4) учитывается третьим, по приоритету «качество > время > цена».
4. Победившая модель и подобранный для неё `effort` фиксируются в `cloud.model` и `cloud.effort`. По тем же прогонам калибруется вес соответствия стилю страницы (FR-11.4).

## 13. Ключевые решения

| ID | Решение | Рассмотренные альтернативы | Почему так |
|---|---|---|---|
| D1 | Python; доступ к Photos через PhotoKit (pyobjc) за интерфейсом `library` | osxphotos: читает приватную базу Photos, требует Full Disk Access, зато даёт оценки Photos и пояс каждого снимка; только Swift; Swift helper-приложение с собственным доступом к Photos | Нужен только доступ Photos, официальный API без чтения приватной базы. Потери — оценки Photos (малый вклад в локальную оценку) и пояс снимка (решается D7). Запасной путь — Swift-хелпер |
| D2 | Двухступенчатая оценка: мусор и дубли локально; первая ступень — Haiku 5.5 (effort `medium`) один проход по всем снимкам со всеми темами запуска и названием альбома, релевантность 1–10, кандидаты от 5; вторая — основная модель по кандидатам каждой темы; лимит $5 на альбом | Локальная модель CLIP/SigLIP для фильтра темы; первая ступень отдельно по каждой теме с «при сомнении — да» (в spike: низкая точность, в ~8 раз дороже); первая ступень на Sonnet 5.5 (в spike: точнее узнаёт места, но ~16× дороже и буквальнее читает темы); Haiku с effort `high` (в spike: без выигрыша); только локально; всё на дорогой модели | Модель, видящая все темы и контекст поездки, различает близкие темы и понимает темы, определённые через другие; первая ступень стоит ~$0.15 на 1000 снимков на запуск; не нужен torch. Цена — превью почти всех снимков уходят в облако, а смена списка тем пересчитывает первую ступень |
| D3 | Тема определяется по содержанию кадра (облачная модель) и/или интервалу времени; геотеги не используются как признак темы | Геотеги; геотег с запасным вариантом по содержанию | Метка в геотеге может быть некорректной |
| D4 | Результат — копии оригиналов в отдельной директории; Photos только на чтение | Альбом в Photos; только отчёт без файлов | Требование пользователя |
| D5 | Live Photo: выбирается лучший кадр анимации; кадр видео только если явно лучше ключевого; сохраняется в TIFF | Только ключевой снимок; ключевой снимок + кадр из видео рядом | Требование пользователя; запас и TIFF компенсируют меньшее разрешение видео |
| D6 | Модели обеих ступеней выбираются в конфиге (вторая — ещё и флагом); отладка на Haiku 5.5 и в режиме без облака; прод-модель второй ступени выбирается сравнением отчётов прогонов | Фиксированная модель; бесплатная локальная мультимодальная модель (Ollama) для отладки; встроенная команда `compare` | Дешёвая и бесплатная отладка при одном провайдере. Ollama — вторая интеграция с иным поведением, результаты отладки на ней не переносятся на Claude. Для сравнения достаточно отчётов с моделью и стоимостью в шапке |
| D7 | Часовой пояс задаётся в `trip.yaml` (`timezone`) или флагом `--timezone`; обязателен, если у тем есть интервалы | Пояс по GPS каждого снимка (офлайн); GPS с запасным поясом поездки; системный пояс Mac | GPS может быть искажён (снимки перекинуты уже дома, сбились настройки фотоаппарата), а пояс поездки пользователь знает всегда, хотя бы на уровне страны |
| D8 | Лента — лучшие кадры поездки; stories — «упрощённая лента» поездки: хорошие кадры по теме, не дотягивающие до ленты. Люди — не критерий ни для одного списка, отсутствие людей не минус | Stories — про людей и эмоции (версия 0.1) | Требование пользователя после прогона на Egypt.26: кадры без людей часто лучше для ленты, stories — продолжение ленты, а не отдельный жанр |
| D9 | Стиль страницы — гибрид: текстовый профиль `style.md`, который один раз пишет сильная модель по опубликованным постам и скриншотам страницы, плюс 1–2 скриншота страницы в каждом запросе второй ступени; соответствие стилю — критерий наравне с композицией и светом | Только текстовый профиль (дешевле, но беднее передаёт вайб); 6–10 образцов-картинок в каждом запросе (~10 тыс. токенов на группу, непрозрачно, что модель взяла); доступ к странице через API Instagram (только бизнес-аккаунты через Facebook) или парсинг (нарушает правила сервиса) | Профиль прозрачен и правится руками, скриншоты дают модели вайб страницы напрямую; цена — ~4 тыс. входных токенов на группу. Выбор пользователя |

## 14. Принятые риски

| Риск | Последствие | Как смягчаем |
|---|---|---|
| PhotoKit через pyobjc: асинхронные вызовы с обработчиками неудобны в Python | Сложнее код адаптера, возможны зависания на загрузке из iCloud | Spike (§11); таймауты на загрузку; запасной путь — Swift-хелпер |
| Первая ступень пропускает подходящие кадры (в spike Haiku и Sonnet расходились на ~10% кадров) | Неполный шорт-лист по теме | Мягкий порог `min_theme_relevance` = 5, вторая ступень перепроверяет соответствие; в отчёте видно, сколько кадров признано подходящими; в теме можно задать интервал |
| Неоднозначная формулировка темы («GEM», «Карнакский музей») или близкие по смыслу темы (маска Тутанхамуна в GEM и Долина Царей) | Кадры уходят не в ту тему | Подсказки по формулировкам (FR-1.2, README); кадр может относиться к нескольким темам (FR-1.5); проверка на приёмке (Task 13) |
| Лимит скорости API (500 000 входных токенов в минуту на Haiku 5.5) | Первая ступень не быстрее ~2 минут на 1000 снимков, ответы 429 | Ограничение параллельности, ожидание и повтор при 429, сохранение каждой обработанной группы в кэш |
| Превью почти всех снимков уходят в Claude API | Фото поездки покидают Mac в уменьшенном виде | Принято пользователем при выборе D2 |
| Оценки модели в разных группах откалиброваны неидеально | Ранжирование между группами неточное | Общая рубрика, распределение групп по черновой оценке, при равенстве — локальная оценка |
| Ориентир стоимости грубый | Превышение NFR-2 | Замер в spike; защита бюджета останавливает запуск до отправки |
| Загрузка превью и оригиналов из iCloud медленная | Превышение NFR-4 | Замер в spike; оригиналы загружаются только для итоговых списков |
| Скачанные оригиналы занимают место на Mac | Рост занятого места на диске | Загружается только шорт-лист (≤ 60 снимков на тему) |
| Промпт, отлаженный на Haiku 5.5, ведёт себя иначе на прод-модели | Качество на проде ниже ожидаемого | Сравнительные прогоны на всех кандидатах в прод-модели (§12) до фиксации модели |
| Профиль стиля неверно передаёт вайб страницы или вес стиля подобран неудачно | Отбор не в стиле страницы, либо стиль вытесняет сильные кадры | `style.md` читается и правится руками; вес калибруется по прогонам (§12) |
| Скриншоты-образцы в каждом запросе второй ступени | Вторая ступень дороже примерно на 20% | `style.reference_images` настраивается, 0 — только текст профиля |
