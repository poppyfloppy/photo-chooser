## 1. Проблема

После путешествий остаётся очень много фотографий. Отбирать их вручную тяжело, процесс затягивается и сходит на нет, а Instagram (лента и stories) так и не ведётся.

## 2. Цель

CLI-приложение для macOS, которое по альбому из Photos и заданным темам собирает **посты на тему**: **карусель** для ленты (по умолчанию одна, до 5 кадров, с обложкой и порядком) с запасными ракурсами к её кадрам и короткий набор **stories** из лучших кадров, не вошедших в карусель. Лучше меньше, но качественно. Финальный выбор делает пользователь. Отобранные кадры дальше обрабатываются в другом инструменте.

Приоритеты при компромиссах: **качество отбора > время > цена**.

## 3. Сценарий использования

1. После поездки пользователь собирает фото поездки в альбом в Photos (~1000 фото).
2. Описывает темы в `trip.yaml` (или задаёт одну тему аргументами CLI): по содержанию («пирамиды, сфинкс»), по интервалу времени («14 марта, 05:00–12:00») или по обоим признакам.
3. Запускает `photo-chooser run trip.yaml` в Terminal. Ключ Claude API один раз сохраняется в Keychain командой `photo-chooser key set` (FR-13).
4. Получает директорию с копиями оригиналов: для каждой темы карусели в `feed/carousel-N <сюжет>/` (с запасными ракурсами в `alternatives/`) и `stories/`, файлы пронумерованы по позиции, рядом `report.md` с причинами выбора.
5. Просматривает посты в Finder, при желании заменяет кадры запасными, обрабатывает их в своём инструменте и публикует.

## 4. Scope

**В scope (MVP):**
- CLI без GUI.
- Чтение альбома Photos через PhotoKit, включая оригиналы в iCloud («Оптимизация хранилища»).
- Фото: HEIC, JPEG, Live Photo. Снимки с RAW обрабатываются по основному файлу (FR-2.2).
- Темы по содержанию кадра (текстовый запрос на любом языке) и/или по интервалу времени.
- Отсев мусора и дублей, двухступенчатая оценка в облаке, сборка постов: карусели ленты и stories.
- Копирование оригиналов в отдельную директорию и отчёт с короткой причиной выбора.
- Выбор моделей Claude и режим без облака для дешёвой и бесплатной отладки.
- Учёт стиля страницы Instagram автора по образцам из Photos (FR-11).
- Снижение стоимости облака: кэш общего мета-блока запросов, модель, `effort` и размер превью по ступеням (FR-8).
- Хранение ключа Claude API в Keychain (FR-13).

**Вне scope:**
- Обработка кадров (перспектива, горизонт, баланс белого и т. п.) — пользователь делает её сам в другом инструменте.
- Видео.
- Любая запись в Photos: альбомы, метки, правки, избранное.
- Общие (shared) альбомы.
- Отдельная поддержка RAW: копирование второй части пары RAW+JPEG/HEIC — позже.
- Публикация в Instagram, подписи, хэштеги.
- Доступ к самой странице Instagram (API, парсинг): образцы стиля берутся из Photos (FR-11).
- Распознавание автора на кадрах по лицу: постановочный портрет на фоне места оценивается по признакам кадра (FR-3 п.8, D14), отличить автора от спутника программа не может.
- GUI.
- Геотеги: метка в геотеге может быть некорректной, поэтому координаты не используются ни для темы, ни для часового пояса.

## 5. Функциональные требования

### FR-1. Входные данные

- **FR-1.1.** Источник — один обычный альбом Photos, указанный по имени.
- **FR-1.2.** Тема задаётся полями:
  - `name` — имя темы, обязательно;
  - `query` — что искать в кадре, текст на любом языке;
  - `from` / `to` — интервал времени.

  Нужен хотя бы один из признаков: `query` или интервал. Если указаны оба, кадр должен удовлетворять обоим.

  Темы с `query` оцениваются на первой ступени вместе, поэтому тема может ссылаться на другие темы запуска («оставшиеся храмы»). Формулировка заметно влияет на результат: аббревиатуры и неоднозначные названия лучше расшифровывать («GEM (Большой Египетский музей)», «Карнакский храм», а не «Карнакский музей»).
- **FR-1.3.** Интервал времени трактуется в **местном времени поездки**: время съёмки снимка переводится в часовой пояс `timezone` из `trip.yaml` (в CLI-режиме — флаг `--timezone`), например `Africa/Cairo`. `timezone` обязателен, если хотя бы у одной темы задан интервал; без него запуск останавливается с ошибкой конфигурации.
- **FR-1.4.** Тема только с интервалом (например, «День 3») означает, что все кадры интервала релевантны и ранжируются только по качеству.
- **FR-1.5.** Один кадр может попасть в несколько тем одного запуска: первая ступень может отнести его к нескольким темам, а вторая ступень и раскладка выполняются по каждой теме отдельно. Внутри одной темы кадр попадает либо в ленту, либо в stories, но не в оба списка.

### FR-2. Типы медиа

- **FR-2.1.** Учитываются фото: HEIC, JPEG, Live Photo. Видео игнорируются.
- **FR-2.2.** RAW в MVP отдельно не поддерживается: у любого снимка копируется только основной файл (ресурс Photo). Для пары RAW + JPEG/HEIC вторая часть не копируется.
- **FR-2.3.** Live Photo см. FR-5.

### FR-3. Конвейер отбора

Общие для всех тем этапы (один раз на запуск; локальные признаки кэшируются по альбому):

1. **Чтение альбома** через PhotoKit (только чтение): снимки с датой, размерами и признаками Live Photo и скриншота.
2. **Превью** с длинной стороной `cloud.screen.preview_px` (по умолчанию 1024): на нём считаются локальные признаки и работает первая ступень; вторая ступень и сборка получают то же превью, уменьшенное до `cloud.judge.preview_px` (по умолчанию 768). Если превью нет на Mac, PhotoKit скачивает его из iCloud. Если превью получить не удалось, снимок пропускается и учитывается в отчёте как «нет превью».
3. **Отсев мусора:**
   - скриншоты (признак PhotoKit). Флаг Apple Vision «утилитарный кадр» для отсева не используется: на альбоме поездки он помечал росписи гробниц, рельефы и музейные экспонаты, а не документы и чеки. Таблички, документы и экраны отсекают облачные ступени;
   - крайний смаз: только почти однородные кадры. Резкость не годится как общий порог: у плавных сюжетов (закат, небо, дымка, вода) она низкая без всякого смаза;
   - полностью пересвеченные или чёрные кадры.

   Порог мягкий: отсекается только явный брак, потому что stories допускают изъяны. Остальной брак оценивают облачные ступени.
4. **Дубли и серии.** Похожие кадры, снятые близко по времени, объединяются в кластер по визуальному отпечатку Vision и времени съёмки. Дальше идёт один представитель кластера — лучший по **локальной оценке качества**: эстетика Vision, резкость, качество лиц. Внутри серии сюжет одинаковый, поэтому сравнение резкости здесь честное.
5. **Первая ступень — отбор по всем темам сразу** (модель и `effort` — `cloud.screen`, по умолчанию `claude-haiku-5-5` и `medium`, один проход на запуск). Все оставшиеся снимки отправляются группами; в каждом запросе — название альбома и пронумерованный список тем запуска с `query`. По каждому снимку возвращается:
   - темы, к которым относится кадр, с релевантностью 1–10 (10 — место или объект темы и есть содержание кадра; темы ниже 5 не указываются). Кадр может относиться к нескольким темам или ни к одной (аэропорт, самолёт, отель);
   - черновая оценка силы кадра, шкала 1–10, по той же рубрике, что и на второй ступени (п.8), без учёта стиля страницы.

   Если в запуске нет тем с `query`, первая ступень не выполняется.

Для каждой темы:

6. **Фильтр интервала**, если он задан (FR-1.3).
7. **Кандидаты.** Тема с `query` — снимки интервала с релевантностью к теме не ниже `min_theme_relevance` (по умолчанию 5: на этой ступени полнота важнее точности, вторая ступень перепроверяет соответствие). Тема только с интервалом — все снимки интервала. Кандидаты сортируются по релевантности, затем по черновой оценке, затем по локальной оценке качества; во вторую ступень идут первые `candidates_per_theme`.
8. **Вторая ступень — оценка** (модель, `effort` и размер превью — `cloud.judge`; по умолчанию `effort` high и 768 px). Кандидаты отправляются группами вместе с описанием темы, профилем стиля и образцами страницы (FR-11). По каждому кадру возвращается:
   - соответствует ли кадр теме;
   - **сила кадра**, шкала 1–10 — одна для поста и stories: сборка кладёт сильнейшие кадры в пост, а следующие по силе — в stories (D13). Главные критерии — эстетика кадра (свет, цвет, композиция, настроение) и соответствие стилю ленты (FR-11.4); техническое качество и познавательность — второстепенные;
   - оценка ставится **по потенциалу после обработки и кадрирования** в стиле страницы (D12): то, что исправляет обработка (экспозиция, цвет и баланс белого, завал горизонта, кадрирование), недостатком не считается; то, что не исправить (смаз, промах фокуса, выбитые света, обрезанный объект), — считается;
   - **люди в кадре** (D14): портрет путешественника — типичная обложка ленты автора и плюс к силе кадра, но только если кадр гармоничен как фотография. Так бывает в двух случаях: человек небольшой на фоне места, фигура целиком, читаются масштаб и перспектива; или это настоящий портрет — малая глубина резкости (боке), красивый свет и цвет, гармоничная композиция. Портрет, который как фотография не работает (ноги или голени срезаны краем кадра, случайная или неловкая поза, человек закрывает объект, слабая композиция), — слабый кадр, его лучше пропустить: кадр не поднимается только потому, что в нём есть путешественник. Толпа, прохожие и случайные туристы, которые отвлекают от места, — недостаток. Отсутствие людей недостатком не считается;
   - **интересное** — да или нет: момент, которому нужен поясняющий текст (что изображено, история места), поэтому он хорош для stories и при средней силе кадра;
   - короткая причина на языке темы: чем кадр хорош или слаб;
   - советов по кадрированию вторая ступень не даёт: их пишет сборка, только для кадров постов (FR-4.2, D10). Подпись перед превью по-прежнему указывает ориентацию: `id: p03 (horizontal)`.

   Кадры, которые модель сочла не соответствующими теме, исключаются. Для темы только с интервалом эта проверка не применяется.
9. **Сборка постов** (FR-4): модель второй ступени собирает из сильнейших кандидатов карусель с запасными ракурсами и stories.
10. **Live Photo** из каруселей, запасных и stories обрабатываются по FR-5.
11. **Экспорт** (FR-6).

В режиме без облака этапы 5 и 8 пропускаются, сборка заменяется раскладкой по локальной оценке (FR-10.2).

**Порядок этапов** (D16). Этапы 6–8 выполняются для всех тем запуска, затем этап 9 — для всех тем, затем этапы 10–11 — по каждой теме. Так запросы второй ступени, а за ними запросы сборки идут подряд с общим мета-блоком и читают его из кэша API (§9). Ошибка API в запросе темы помечает эту тему «не обработана», остальные темы продолжаются (§9, «Ошибки»).

### FR-4. Посты: карусель ленты и stories

- **FR-4.1. Кандидаты сборки.** Из оценённых второй ступенью кадров темы, которые подходят к теме (для темы только с интервалом — все оценённые) и имеют силу не ниже `min_score` или пометку «интересное», берутся до `cloud.compose_candidates` (по умолчанию 30) по силе кадра; при равенстве — по локальной оценке качества. «Интересные» кадры, не вошедшие в это число, добавляются сверх него по силе, но не больше `posts.stories`: иначе момент для stories с поясняющим текстом теряется за сильными кадрами. Если кандидатов нет, сборка не вызывается, отчёт выходит с пустыми постами.
- **FR-4.2. Запрос сборки** — один на тему, к модели второй ступени (`cloud.judge`: модель, `effort`, размер превью). В запросе: текст профиля стиля и скриншоты-образцы (FR-11.4), превью кандидатов с подписью `id: c07 (horizontal) · сила 8 · интересное · «причина»` (пометка — только у интересных), тема. Модель видит кандидатов вместе и собирает из них посты, выбирая прежде всего по эстетике и соответствию стилю (D13). Брать всех кандидатов не нужно: кадр, который автор не опубликует, в посты не попадает.
  - **карусель ленты** — сильнейший сюжет темы. Сюжет выбирается по кадрам вместе — по свету и эстетике набора и разнообразию планов, а не по самым высоким отдельным оценкам; какой свет сильнее, зависит от места (золотой час на камне древнего храма, огни ночного мегаполиса). Карусель держится в одном ключе (сквозная связность): место — улица или помещение, свет, время суток; одиночный кадр из другого ключа, например интерьер среди уличных видов, уходит в stories. По умолчанию одна карусель (`posts.carousels`, по умолчанию 1), не больше `posts.carousel_size` кадров (по умолчанию 5; обычно 3–5), с коротким названием сюжета на языке темы. Первый кадр — обложка: самый сильный и характерный для сюжета, в том числе гармоничный портрет автора (D14); портрет ради портрета в карусель не добавляется; дальше — порядок, который рассказывает историю. Каждый слайд добавляет новое: один объект может появиться несколько раз, если слайды показывают его по-разному (например, общий вид, объект на фоне другой достопримечательности, деталь крупно); два слайда с одинаковым планом почти с одной точки не допускаются — более слабый уходит в запасные. Только то, что автор опубликует: лучше меньше, но качественно. Вторая карусель — только при `posts.carousels` ≥ 2 и для отдельного сюжета темы, в котором не меньше 4 сильных кадров; при одной карусели другой сюжет уходит в stories;
  - **запасные ракурсы** — у каждого кадра карусели до 2 альтернатив: другие ракурсы того же момента, которые можно поставить вместо основного;
  - **stories** — не больше `posts.stories` (по умолчанию 9), тоже «лучше меньше»: лучшие из кадров, не вошедших в карусель и запасные, в том числе другой сюжет темы (`best`), — без повторов плана слайдов карусели и без недостатков, которые обработка не исправит, — и интересное, которому нужен поясняющий текст (`interesting`); у интересного — подсказка на языке темы, что пояснить (готовую подпись модель не пишет).
  - **советы по кадрированию** (D10) — у горизонтального или квадратного слайда карусели короткий совет на языке темы, что оставить в кадре при кадрировании до 4:5, у такой же story — до 9:16. У вертикальных кадров совет пустой, у запасных ракурсов советов нет.
- **FR-4.3. Проверка ответа.** Неизвестные id отбрасываются; каждый кадр используется один раз — в карусели, среди запасных или в stories (при повторе засчитывается первое появление); лишнее обрезается до лимитов FR-4.2. Stories упорядочиваются по времени съёмки, как дневник поездки; порядок, в котором их вернула модель, не используется.
- **FR-4.4. Сбой сборки** (отказ модели, неразборчивый ответ, ошибка API после повторов; ошибки ключа, доступа и баланса останавливают запуск, §9): тема раскладывается по оценкам — одна карусель из сильнейших кадров не ниже `min_score` (до `posts.carousel_size`), stories — следующие по силе не ниже `min_score` (до `posts.stories`) в порядке съёмки, без запасных, подсказок и советов по кадрированию; в отчёте предупреждение «разложено по оценкам», остальные темы продолжаются.
- **FR-4.5.** Недобора нет: если сильных кадров мало, карусель короче или её нет — это норма («лучше меньше»).

### FR-5. Live Photo

- **FR-5.1.** Live Photo рассматривается как короткая анимация. Кандидаты на итоговый кадр — ключевой снимок и кадры видеочасти.
- **FR-5.2.** Кадры оцениваются локально: резкость, эстетика, качество лиц (открытые глаза).
- **FR-5.3.** У ключевого снимка разрешение выше, поэтому кадр видеочасти выбирается, только если он **явно** лучше: превосходит ключевой снимок на величину `live_frame_margin` из конфига.
- **FR-5.4.** Если выбран ключевой снимок, копируется его оригинал (HEIC/JPEG). Если выбран кадр видео, он сохраняется в **TIFF** (без потерь), в него переносятся дата и геоданные из оригинала, имя файла получает суффикс `_live-frame`. В отчёте указывается, что разрешение кадра ниже оригинала.
- **FR-5.5.** Видеочасть скачивается из iCloud только для Live Photo, попавших в карусели, запасные или stories. Если скачать её не удалось, копируется оригинал ключевого снимка, в отчёте — пометка.

### FR-6. Результат

- **FR-6.1.** Каждый запуск пишет в новую директорию и ничего не перезаписывает:

  ```
  <output_dir>/<альбом>/<YYYY-MM-DD_HHMM>/
    <тема>/
      feed/carousel-1 Пирамиды и Сфинкс/01_IMG_4521.HEIC    ← обложка
      feed/carousel-1 Пирамиды и Сфинкс/02_IMG_4533.JPG
      feed/carousel-1 Пирамиды и Сфинкс/alternatives/01a_IMG_4519.HEIC
      stories/01_IMG_4610_live-frame.tiff                   ← stories по времени съёмки
      report.md
  ```

- **FR-6.2.** Копируются **оригиналы**, без правок, сделанных в Photos. Двузначный префикс в имени — позиция в карусели или в stories; у запасного кадра — номер слота и буква (`03a_`, `03b_`). Название сюжета входит в имя папки карусели (не длиннее 60 знаков). Если оригинал кадра карусели не скачался, на его место встаёт первая альтернатива слота; если альтернатив нет, слот выпадает с пометкой в отчёте.
- **FR-6.3.** `report.md` на тему содержит:
  - шапку: модель, `effort` и размер превью каждой ступени (или «без облака»), версия промпта, профиль стиля (дата и отпечаток `style.md`, число скриншотов-образцов) или предупреждение о его отсутствии (FR-11.5) — чтобы прогоны на разных моделях можно было сравнивать;
  - пояснение перед таблицами: «Оценка» — сила кадра по второй ступени, 1–10, «Причина» — её пояснение к оценке, а не решение сборки;
  - по каждой карусели — название сюжета и таблицу: слайд, файл, оценка, ориентация, пометки (кадр из Live Photo, замена альтернативой), причина, кадрирование до 4:5 (совет сборки), запасные;
  - таблицу stories в порядке съёмки: номер, файл, оценка, тип (лучшее / интересное), что пояснить, причина, кадрирование до 9:16 (совет сборки); у вертикальных кадров, без облака и при раскладке по оценкам — «—»;
  - сводку: сколько снимков прочитано, без превью, отсеяно как мусор, схлопнуто как дубли, прошло интервал, признано подходящими к теме на первой ступени, отправлено на вторую ступень, отправлено в сборку; итог «каруселей N (кадров по каруселям), stories M»; стоимость первой ступени (общая на запуск), второй и сборки (по теме), накопленная стоимость по альбому; токены кэша мета-блока во второй ступени и сборке темы — записано и прочитано (§9); токены по ступеням — вход, выход (с thinking) и кэш: первая ступень — общие на запуск, вторая ступень и сборка — по теме; время первой ступени, второй ступени и сборки за запуск; предупреждение FR-4.4, если сборка не удалась; пропущенные снимки с причиной.

### FR-7. CLI

```
photo-chooser albums                     # список альбомов Photos
photo-chooser run trip.yaml              # все темы из файла поездки
photo-chooser run --album "Египет 2026" --theme "Гиза" --query "пирамиды, сфинкс" \
                  [--from "2026-03-12 06:00" --to "2026-03-12 14:00"] [--timezone Africa/Cairo]
photo-chooser run ... --dry-run          # только локальные этапы + оценка стоимости
photo-chooser run ... --max-cost 8       # разово поднять лимит бюджета
photo-chooser run ... --model claude-sonnet-5-5   # модель второй ступени для этого запуска
photo-chooser run ... --no-cloud         # без Claude: только локальные оценки, бесплатно
photo-chooser style [--yes]              # построить профиль стиля страницы Instagram (FR-11)
photo-chooser key set                    # сохранить ключ Claude API в Keychain (FR-13)
photo-chooser key delete [--yes]         # удалить ключ из Keychain
photo-chooser key status                 # откуда будет взят ключ; сам ключ не выводится
```

`--timezone` обязателен вместе с `--from` / `--to` (FR-1.3).

- **FR-7.1.** `--dry-run` выполняет общие этапы 1–4 и фильтр интервала, выводит число снимков по темам и оценку стоимости (FR-9.1): первая ступень — один проход по всем снимкам после отсева, вторая — `candidates_per_theme` кандидатов на тему, сборка — один запрос на тему с `compose_candidates` превью и «интересными» сверх них (до `posts.stories`, FR-4.1); уже закэшированная работа не считается. Режим не обращается к Claude и ничего не копирует.
- **FR-7.2. Ход запуска.** `run` пишет, что происходит, чтобы было видно, идёт работа или запрос завис: превью и локальные признаки — каждые 50 снимков; первая ступень — сколько снимков взято из кэша и ход по группам; по каждой теме — вторая ступень (кандидатов, из кэша, ход по группам со временем) и сборка постов (модель, время, итог). Если ответа нет дольше 30 секунд, каждые 30 секунд выводится строка ожидания с прошедшим временем. Паузы из-за лимита скорости и повторы запроса после таймаута или сбоя сети тоже выводятся. Таймаут одного запроса — 5 минут. Первый запрос второй ступени и первый запрос сборки идут одни, остальные — после их ответа (запись кэша, §9); это видно по ходу групп.

### FR-8. Конфигурация

Общий конфиг `~/.config/photo-chooser/config.yaml`:

```yaml
output_dir: ~/Pictures/photo-chooser
posts:                             # посты на тему (FR-4)
  carousels: 1                     # каруселей ленты, не больше
  carousel_size: 5                 # кадров в карусели, не больше
  stories: 9                       # stories, не больше
cloud:
  screen:                          # первая ступень — отбор (FR-3 п.5)
    model: claude-haiku-5-5
    effort: medium
    preview_px: 1024               # превью первой ступени и локальных признаков
  judge:                           # вторая ступень и сборка постов (FR-3 п.8, FR-4.2), D18
    model: claude-haiku-5-5        # на время отладки, прод-модель фиксируется по §12
    effort: high
    preview_px: 768                # то же превью, уменьшенное для второй ступени и сборки
  pricing:                         # $ за 1 млн токенов: вход / выход / чтение кэша (FR-9.2)
    claude-haiku-5-5:  {input: 0.10, output: 0.50, cache_read: 0.01}
    claude-sonnet-5-5: {input: 2.00, output: 10.00, cache_read: 0.10}
    claude-opus-5-5:   {input: 4.00, output: 20.00, cache_read: 0.20}
  max_cost_usd_per_album: 5.0      # лимит накопленной стоимости по альбому, обе ступени
  candidates_per_theme: 100        # сколько кадров первая ступень передаёт второй
  group_size: 20
  compose_candidates: 30           # сколько сильнейших кадров темы видит сборка постов (FR-4.1)
thresholds:                        # значения по умолчанию — docs/spike-findings.md
  min_theme_relevance: 5           # порог релевантности первой ступени для кандидатов
  junk_blur: …
  duplicate_distance: …
  min_score: 5                     # порог силы кадра для кандидатов сборки и раскладки по оценкам (было: лента 6, stories 4)
  live_frame_margin: …
style:                             # стиль страницы Instagram (FR-11)
  albums: [Snapseed, Instasize]    # опубликованные посты; одноимённые альбомы берутся все
  since: 2018-01-01                # более старые снимки не берутся
  screenshots_album: Instagram style   # скриншоты гридов и подборок stories
  sample: 40                       # сколько постов отправить при построении профиля
  model: claude-opus-5-5           # модель, которая пишет профиль (разово)
  reference_feed: 2                # скриншотов ленты в запросах второй ступени и сборки (первые в альбоме)
  reference_stories: 2             # скриншотов stories (следующие за ними)
```

Если `cache_read` для модели не задан, чтение кэша считается как 0.1 × цены входа.

Прежние `shortlist.feed` / `shortlist.stories` (версии 0.1–0.2), `style.reference_images` и `thresholds.min_feed_score` / `thresholds.min_stories_score` (версии 0.2–0.3) больше не поддерживаются: запуск останавливается с ошибкой конфигурации и подсказкой, чем их заменить.

Прежние ключи `cloud.screen_model`, `cloud.model`, `cloud.effort`, `cloud.preview_long_side_px` (версии 0.1–0.5) и `cloud.batch` (версия 0.5) тоже не поддерживаются: ошибка конфигурации с готовым фрагментом `cloud.screen` / `cloud.judge` на замену.

Файл поездки `trip.yaml`:

```yaml
album: "Египет 2026"
timezone: Africa/Cairo              # обязателен, если у какой-либо темы есть интервал
themes:
  - name: Гиза
    query: "пирамиды, сфинкс, верблюды на фоне пирамид"
  - name: Абу-Симбел
```

Ключ Claude API в конфиге не хранится: он берётся из Keychain, `ANTHROPIC_API_KEY` или профиля `ant auth login` (FR-13). В режиме `--no-cloud` ключ не нужен.

### FR-9. Бюджет и кэш

- **FR-9.1.** Перед облачными этапами рассчитывается оценка стоимости обеих ступеней и сборки по всем темам запуска. Если **накопленная стоимость по альбому + оценка** превышает `max_cost_usd_per_album`, запуск останавливается до отправки чего-либо в облако и выводит оценку. Разово поднять лимит можно флагом `--max-cost`. Картинки каждой ступени считаются по её размеру превью. Экономия кэша мета-блока в оценку не входит: попадание в кэш не гарантировано, поэтому оценка чуть выше факта.
- **FR-9.2.** Фактическая стоимость считается по `usage` ответов API: входные токены по цене входа; запись в кэш — 1.25 × цены входа (TTL 5 минут); чтение из кэша — по `cache_read` из `cloud.pricing`; выходные токены по цене выхода. Стоимость записывается в кэш и в отчёт.
- **FR-9.3.** Кэш (SQLite, `~/Library/Caches/photo-chooser/`):
  - локальные признаки хранятся по снимку (идентификатор PhotoKit);
  - оценки первой ступени — по ключу «снимок × набор тем (хэш названия альбома и списка тем с `query`) × модель × версия промпта, `effort` и размер превью ступени»: изменение списка тем запускает первую ступень заново;
  - оценки второй ступени — по ключу «снимок × тема (хэш name+query+интервал) × модель × версия промпта, `effort` и размер превью ступени и отпечаток профиля стиля (хэш `style.md` и выбранных скриншотов-образцов)»: правка профиля или смена скриншотов пересчитывает вторую ступень, первая остаётся в кэше;
  - сборка постов — по ключу «тема × модель × версия промпта сборки с `effort` и размером превью × отпечаток входа (id кандидатов с оценками и отпечаток профиля стиля)»: повтор той же темы бесплатен, изменение оценок или профиля собирает тему заново.

  Повторный запуск той же темы не платит за облако повторно и продолжает работу с места сбоя.

### FR-10. Выбор модели и режим без облака

- **FR-10.1. Выбор модели.** Модель первой ступени задаётся в `cloud.screen.model`, второй ступени и сборки — в `cloud.judge.model`; флаг `--model` переопределяет `cloud.judge.model` на один запуск. Поддерживаются модели Claude с приёмом изображений; проверяются `claude-haiku-5-5`, `claude-sonnet-5-5`, `claude-opus-5-5`. Если для модели нет цены в `cloud.pricing`, запуск останавливается до отправки в облако: без цены нельзя проверить бюджет (FR-9.1).
- **FR-10.2. Режим без облака** (`--no-cloud`). Обе облачные ступени пропускаются, Claude не вызывается, стоимость $0. Назначение режима — бесплатная отладка механики (чтение альбома, отсев, дубли, раскладка, экспорт, отчёт), а не качество отбора. Правила:
  - `query` игнорируется, тема фильтруется только интервалом; если интервала нет, кандидаты — все снимки после отсева. В отчёте — предупреждение;
  - сборка не вызывается: одна карусель — `posts.carousel_size` лучших по локальной оценке качества, stories — следующие `posts.stories` в порядке съёмки, без запасных и подсказок;
  - порог `min_score` не применяется: он задан в шкале оценок модели;
  - причина в отчёте — составляющие локальной оценки (эстетика, резкость, лица).
- **FR-10.3. Отладка** идёт на `claude-haiku-5-5` для обеих ступеней и в режиме без облака.
- **FR-10.4. Выбор прод-модели второй ступени** — прогоны одних и тех же тем на разных моделях с ручным сравнением `report.md` (§12). Кэш разделяет оценки по модели (FR-9.3), каждый прогон пишет в свою директорию (FR-6.1), поэтому прогоны не смешиваются. Сравнительные прогоны расходуют общий лимит альбома; при необходимости он поднимается флагом `--max-cost`.

### FR-11. Стиль страницы Instagram

- **FR-11.1. Образцы.** Опубликованные посты — снимки из альбомов Photos `style.albums` (одноимённые альбомы берутся все, повторы снимков между альбомами убираются), снятые не раньше `style.since`. Скриншоты страницы — гриды ленты и подборки stories — из альбома `style.screenshots_album`. К самой странице Instagram программа не обращается.
- **FR-11.2. Построение профиля** — команда `photo-chooser style`:
  - выбирает `style.sample` постов: чем новее снимок, тем чаще он попадает в выборку (примерно половина выборки — из самой новой четверти снимков, дальше реже, вплоть до `style.since`);
  - добавляет скриншоты страницы, не больше 12;
  - отправляет их одним запросом модели `style.model` (`effort` — из `cloud.judge`); каждый образец подписан типом («пост» или «скриншот страницы») и месяцем съёмки;
  - модель пишет описание стиля на русском, около 300 слов, с разделами «Лента» и «Stories»: обработка, свет и цвет, композиция, типичные сюжеты, чего на странице не бывает; свежие посты весомее старых. Наличие или отсутствие людей чертой стиля не считается; исключение — постановочный портрет автора на фоне места, его модель может назвать чертой ленты (D14);
  - перед отправкой выводит число изображений и оценку стоимости и ждёт подтверждения; флаг `--yes` подтверждает заранее;
  - если постов-образцов меньше 10, останавливается с сообщением.
- **FR-11.3. Профиль** сохраняется в `~/.config/photo-chooser/style.md`, прежний переименовывается в `style.prev.md`. Файл можно читать и править руками.
- **FR-11.4. Использование** — на второй ступени (FR-3 п.8) и в сборке постов (FR-4.2). В каждый запрос добавляются текст профиля и скриншоты из `style.screenshots_album` в порядке альбома (порядок задаёт пользователь в Photos): первые `style.reference_feed` — гриды ленты, следующие `style.reference_stories` — stories; с длинной стороной 1568 px, подписанные «скриншот страницы — лента» или «— stories» и помеченные как образцы, которые не оцениваются. Соответствие стилю вместе с эстетикой кадра — главные критерии силы кадра и выбора в сборке (FR-3 п.8, FR-4.2): по итогам приёмки версии 0.3 их вес поднят над техникой и познавательностью (§12). Сила кадра оценивается по разделу профиля «Лента»; раздел «Stories» и скриншоты stories сборка использует при выборе stories.
- **FR-11.5. Без профиля** — если `style.md` нет, вторая ступень идёт без стиля, в шапке отчёта предупреждение «Профиль стиля не найден — выполните `photo-chooser style`». В режиме `--no-cloud` стиль не используется.
- **FR-11.6. Стоимость.** Расход команды `style` записывается в кэш расходов отдельно от бюджета альбома (FR-9.1). Скриншоты-образцы и текст профиля входят в оценку стоимости второй ступени и сборки и в проверку ценового порога запроса.

### FR-12. Пакетный режим

Удалён в версии 0.5.1 (D16): на проверке 0.5 пакеты второй ступени считались 4–4.5 часа против ~8 минут синхронно — ожидание выросло на порядки.

### FR-13. Ключ Claude API

- **FR-13.1. Источники** по порядку: запись Keychain `anthropic-api-key` в связке входа пользователя, затем переменная `ANTHROPIC_API_KEY`, затем профиль `ant auth login`. Keychain читается системной утилитой `/usr/bin/security`; ключ приходит через её вывод, а не через аргументы, и передаётся клиенту SDK явно. С `--no-cloud` и `--dry-run` ключ не нужен.
- **FR-13.2. `photo-chooser key set`** сохраняет или заменяет ключ. Команда запускает `security add-generic-password`, и утилита сама дважды спрашивает ключ со скрытым вводом: ключ не проходит через photo-chooser, аргументы процессов и историю shell. Существующая запись обновляется на месте, с тем же аккаунтом; новая создаётся с аккаунтом — именем пользователя macOS.
- **FR-13.3. `photo-chooser key delete`** удаляет запись после подтверждения (`--yes` подтверждает заранее). **`photo-chooser key status`** выводит, откуда будет взят ключ: Keychain, `ANTHROPIC_API_KEY`, профиль `ant` или «не найден». Сам ключ не выводится и в API не проверяется.
- **FR-13.4.** Если ключа нет ни в одном источнике, запуск с облаком останавливается до чтения альбома с подсказкой `photo-chooser key set`.

## 6. Нефункциональные требования

| ID | Требование | Как проверяется |
|---|---|---|
| NFR-1 | Медиатека Photos не изменяется (только чтение) | В адаптере Photos нет методов записи, изменяющие вызовы PhotoKit не используются. Интеграционный тест сравнивает состав альбома и даты изменения снимков до и после прогона |
| NFR-2 | Стоимость облачной части (обе ступени) на альбом ~1000 фото ≤ $5 | Защита бюджета (FR-9.1) и фактическая стоимость в отчёте |
| NFR-3 | Качество: в каруселях темы не меньше 2/3 кадров, которые пользователь готов обработать и опубликовать без замены; в stories — не меньше 2/3 пригодных | Ручная оценка пользователем на альбоме прошлой поездки |
| NFR-4 | Первый прогон альбома ~1000 фото ≤ 30 мин; повторный прогон той же темы ≤ 5 мин | Замер на альбоме прошлой поездки |
| NFR-5 | Приложению нужен только доступ к Photos, без Full Disk Access | Запуск из Terminal, у которого в System Settings → Privacy & Security выдан только доступ Photos |
| NFR-6 | Ключ Claude API не хранится в репозитории, конфигах и файлах программы, не передаётся в аргументах процессов и не попадает в вывод, логи и отчёты | Ключ — в Keychain (FR-13). Юнит-тесты: порядок источников ключа, команды `key` с заглушкой `security`, ключ не попадает в аргументы её вызова |

## 7. Архитектура

**Стек:** Python 3.12; доступ к Photos через PhotoKit (`pyobjc-framework-Photos`); Apple Vision и AVFoundation через `pyobjc`; Claude API через официальный Python SDK `anthropic`.

**Модули** (пакет `photo_chooser`). Внешние системы спрятаны за интерфейсами:

| Модуль | Ответственность |
|---|---|
| `library` | Доступ к Photos **только на чтение** через PhotoKit: список альбомов, снимки альбома (идентификатор, имя файла, дата, тип: Live Photo/скриншот, размеры), превью, экспорт оригинала и видеочасти Live Photo с загрузкой из iCloud. Интерфейс позволяет заменить реализацию Swift-хелпером |
| `vision` | Обёртки над Apple Vision: эстетическая оценка, визуальный отпечаток, качество лиц |
| `analysis` | Отсев мусора, кластеры дублей, локальная оценка качества, выбор кадра Live Photo |
| `judge` | Claude: обе ступени (отбор и оценка) и сборка постов — группы, запрос со структурированным ответом (JSON-схема), кэш мета-блока, оценка стоимости, защита бюджета. Раннеры собирают задания (запрос и обработчик ответа), отправка — синхронная, за общим интерфейсом: параллельные запросы, повторы, паузы при 429 |
| `keychain` | Ключ Claude API в Keychain через `/usr/bin/security`: чтение, запись, удаление, источник ключа (FR-13) |
| `style` | Профиль стиля страницы: выбор образцов из Photos, запрос к Claude, `style.md`, отпечаток профиля для ключа кэша, скриншоты-образцы для второй ступени (FR-11) |
| `select` | Чистая логика: кандидаты сборки (FR-4.1), проверка ответа сборки (FR-4.3), раскладка по оценкам при сбое (FR-4.4) и по локальным оценкам в режиме без облака (FR-10.2) |
| `export` | Копирование оригиналов, сохранение кадра Live Photo в TIFF с метаданными, `report.md` |
| `cache` | SQLite-кэш признаков, оценок, сборок и учёта стоимости |
| `config` / `cli` | Загрузка и валидация `config.yaml` / `trip.yaml`, команды CLI, в том числе `key` |

**Поток данных** (FR-3, «Порядок этапов»):

```
альбом → снимки + превью → [мусор] → [кластеры дублей] → признаки (кэш)
  → 1-я ступень: отбор по всем темам (кэш, синхронно)
  → по темам: [интервал] → кандидаты
  → 2-я ступень: оценка кандидатов всех тем (кэш)
  → сборка постов всех тем (кэш)
  └─ для каждой темы: Live Photo → export + report.md
```

## 8. Внешние ограничения

- macOS 26 (Tahoe), Apple Silicon.
- Медиатека Photos с включённой «Оптимизацией хранилища»: оригиналы лежат в iCloud и скачиваются по требованию.
- Terminal, из которого запускается приложение, один раз получает доступ **Photos** (запрос macOS при первом обращении). Full Disk Access не нужен. Приложение проверяет доступ и подсказывает, что сделать.
- PhotoKit не отдаёт часовой пояс снимка и оценки качества, которые считает сам Photos. Пояс определяется по FR-1.3, оценки Photos не используются.
- Видеочасть Live Photo имеет заметно меньшее разрешение, чем ключевой снимок.
- Для облачных ступеней нужен ключ Claude API, использование платное. Ключ хранится в связке входа Keychain; если связка заблокирована, при чтении ключа macOS сама попросит пароль.
- На первой ступени в Claude API уходят превью почти всех снимков альбома (после отсева мусора и дублей); на второй — превью кандидатов.

## 9. Интеграции

### Photos (PhotoKit через pyobjc)

- Альбом — по имени среди обычных альбомов пользователя.
- Снимки: дата создания, размеры, признаки Live Photo и скриншота, ресурсы снимка (основное фото, видеочасть Live Photo).
- Превью — через менеджер изображений PhotoKit с разрешением загрузки из iCloud.
- Оригиналы и видеочасть — запись ресурсов в файл с разрешением загрузки из iCloud.
- Побочный эффект загрузки: Photos может временно хранить скачанные файлы на Mac. Содержимое медиатеки (правки, альбомы, метаданные) при этом не меняется.
- Ошибка загрузки обрабатывается так: повтор до 3 раз, затем снимок пропускается, в отчёт записывается причина. На место кадра карусели встаёт первая альтернатива слота (FR-6.2); кадр stories не заменяется.

### Apple Vision / AVFoundation (через pyobjc)

- Vision даёт эстетическую оценку, визуальный отпечаток для поиска дублей и качество лиц.
- AVFoundation извлекает кадры видеочасти Live Photo.

### Claude API

- **Модели:** первая ступень — `cloud.screen.model`, вторая ступень и сборка — `cloud.judge.model` или флаг `--model` (FR-10); `effort` и размер превью — в тех же секциях (D18). Отладка — `claude-haiku-5-5` на обеих ступенях, прод-модель второй ступени выбирается по §12.
- **Вход:** превью кадров: у первой ступени — `cloud.screen.preview_px` (по умолчанию 1024), у второй ступени и сборки — `cloud.judge.preview_px` (по умолчанию 768), группы по `group_size` (по умолчанию 20). Первая ступень — с названием альбома и списком всех тем с `query`; вторая — с описанием одной темы, общей рубрикой оценки, текстом профиля стиля и скриншотами-образцами страницы с длинной стороной 1568 px (FR-11.4). Сборка постов — один запрос на тему с до `compose_candidates` превью и «интересными» сверх них, с силой кадра и причинами (FR-4.1, FR-4.2). Построение профиля — один запрос с ~50 образцами (FR-11.2). На второй ступени кандидаты распределяются по группам так, чтобы в каждой был разброс черновых оценок.
- **Выход:** структурированный JSON по схеме. Первая ступень: `id`, `matches` (номер темы + релевантность 1–10), `score`. Вторая: `id`, `matches_theme`, `score`, `interesting`, `reason`. Сборка: `carousels` (`title`, `slides` — `id`, `alternatives`, `crop`), `stories` (`id`, `kind`: `best` | `interesting`, `hint`, `crop`); `crop` — совет по кадрированию до 4:5 у слайдов и до 9:16 у stories, пустой у вертикальных кадров.
- **Кэш запросов** (prompt caching, D15) — всегда включён для второй ступени и сборки:
  - общий префикс запросов — system (рубрика и профиль стиля) и скриншоты-образцы; он одинаков для всех тем запуска и для следующих запусков, пока профиль не меняется. Метка `cache_control` стоит на последнем блоке префикса: на последнем скриншоте, без скриншотов — на system. Тема и превью кандидатов идут после метки. У второй ступени и сборки system разный, поэтому записей в кэше API две;
  - TTL — 5 минут: запросы идут подряд и держат кэш тёплым. Минимальный кэшируемый префикс у моделей 5.5 — 512 токенов;
  - запись кэша читается только после ответа на запрос, который её создал, поэтому первый запрос второй ступени и первый запрос сборки идут одни, остальные — после ответа;
  - ответы модели от кэша не меняются, поэтому версии промптов и ключи локального кэша (FR-9.3) остаются прежними;
  - первая ступень без кэша: её префикс — короткий system на Haiku, экономия меньше цента на запуск;
  - цены — FR-9.2: запись 1.25 × цены входа, чтение — `cache_read` (у Opus 5.5 — $0.20 за 1 млн токенов, 0.05 × цены входа).
- **Ключ** — из Keychain, `ANTHROPIC_API_KEY` или профиля `ant auth login` (FR-13).
- **Оценка стоимости:** перед отправкой, по формуле токенов на превью (≈ ширина × высота / 750; в spike — ~1015 токенов на превью 1024 px).
- **Лимит скорости:** у организации пользователя 500 000 входных токенов в минуту на Haiku 5.5. Запросы идут с ограничением параллельности и ожиданием при ответе 429; первая ступень по ~1000 снимкам занимает не меньше ~2 минут.
- **Ошибки:**
  - таймаут запроса 5 минут; повторы после таймаута, сбоя сети и ошибки сервера (до 4) и ожидание при ответе 429 видны в выводе (FR-7.2);
  - обработка `stop_reason: refusal`;
  - если тема всё равно не обработана, остальные темы продолжаются, а отчёт её помечает. В синхронном режиме после ошибки оставшиеся запросы этой темы не отправляются;
  - ошибки ключа (401) и доступа (403) останавливают запуск;
  - ошибка баланса — 402 `billing_error` или 400 с «credit balance is too low» — тоже останавливает запуск, а не раскладывает тему по оценкам: остальные темы упали бы так же. Сообщение: «На балансе Claude API не хватает средств — пополните баланс в Claude Console. Оплаченное сохранено в кэше, повторный запуск продолжит». Код выхода — 6.
- **Ориентир стоимости** (по замерам spike): первая ступень на Haiku 5.5 — ~$0.15 на 1000 снимков после отсева, **один раз на запуск** независимо от числа тем. Вторая ступень по ~100 кандидатам на тему:

  | Модель второй ступени | ≈ за тему | Тем в лимит $5 (с первой ступенью) |
  |---|---|---|
  | `claude-haiku-5-5` | ~$0.02 | больше 100 |
  | `claude-sonnet-5-5` | ~$0.3–0.4 | ~12 |
  | `claude-opus-5-5` | ~$0.7–1.0 | 5–6 |

  С версии 0.3 к теме добавляется сборка постов — один запрос с ~30 превью (~32 тыс. входных токенов): на Opus 5.5 ≈ $0.19, на Haiku — пренебрежимо. С четырьмя скриншотами-образцами (FR-11.4) тема на Opus выходит около $1, в лимит $5 — 4–5 тем на альбом; больше — разово `--max-cost`.

  Цена Haiku 5.5 действует для запросов до 100K токенов; запрос с группой из 20 превью и двумя скриншотами-образцами укладывается в этот предел.

  Стиль страницы (FR-11): построение профиля на `claude-opus-5-5` — ≈ $0.25 разово; скриншоты-образцы и профиль добавляют ~4 тыс. входных токенов на группу второй ступени (на Opus 5.5 ≈ +$0.07 на тему из 100 кандидатов, на Haiku — пренебрежимо).

  Версия 0.5: прогон шести тем на Opus 5.5 (`2026-11-03_0133`) стоил $5.75 — вторая ступень 74 %, сборка 24 %, первая ступень 2 %. Проверка 0.5 на Sonnet 5.5: синхронно три темы — ≈ $1.16 за ~8 минут, кэш мета-блока (~9.5 тыс. токенов) дал около −18 %; пакеты второй ступени считались 4–4.5 часа (D16). Версия 0.5.1: превью второй ступени и сборки 768 px вместо 1024 — около −44 % токенов на картинку, `effort` high — больше выходных токенов; итог проверяется прогоном на Opus против `2026-11-03_0133`.

## 10. Тестирование

- **Юнит-тесты (pytest)**, Photos и Claude заменены заглушками:
  - валидация конфигов и тем;
  - перевод времени съёмки в пояс поездки, интервалы, обязательность `timezone` при интервалах;
  - кластеризация дублей на синтетических векторах;
  - обе ступени: группы, отбор кандидатов, обработка пропусков и refusal;
  - раскладка по оценкам при сбое сборки и без облака (FR-4.4, FR-10.2): порог, лимиты, короткая карусель при нехватке кадров (FR-4.5), stories в порядке съёмки;
  - ход запуска (FR-7.2): строки этапов и групп, ожидание ответа, паузы и повторы, таймаут запроса;
  - нумерация и имена файлов, суффикс `_live-frame`;
  - генерация `report.md`;
  - защита бюджета и кэш;
  - выбор модели и остановка для модели без цены в `pricing`; режим без облака (FR-10.2);
  - стиль (FR-11): выбор образцов (давность, повторы между альбомами, минимум постов), запрос построения профиля и запись `style.md`, профиль и скриншоты в запросе второй ступени, ключ кэша по отпечатку профиля, работа без профиля;
  - советы по кадрированию (D10): поле `crop` в ответе сборки у слайдов и stories, колонки отчёта из ответа сборки, пустой совет у вертикальных кадров, «—» при раскладке по оценкам; в ответе второй ступени советов нет;
  - сборка постов (FR-4): выбор кандидатов («интересные» сверх окна), запрос (подписи с силой кадра и пометкой «интересное», скриншоты ленты и stories), проверка ответа (неизвестные id, повторы, лимиты, stories по времени съёмки), раскладка по оценкам при сбое, кэш сборки, папки каруселей и запасных, замена упавшего слота альтернативой, отчёт с пояснением оценки, ошибка конфигурации на старые `shortlist.*` и `thresholds.min_feed_score` / `min_stories_score`;
  - одна оценка силы кадра (D13) и портрет автора (D14): поля ответа обеих ступеней, рубрика в промптах без «кадры без людей сильнее», пометка «интересное»;
  - кэш мета-блока (D15): метка `cache_control` на последнем блоке общего префикса, первый запрос этапа идёт один; стоимость по полям `usage` с записью и чтением кэша; строка кэша в отчёте;
  - конвейер по этапам (D16): вторая ступень всех тем, затем сборка всех тем; ошибка API темы не останавливает другие темы;
  - ключ (FR-13): порядок источников, команды `key` с заглушкой `security`, ключ не попадает в аргументы её вызова;
  - ошибка баланса останавливает запуск;
  - настройки ступеней (D18): секции `cloud.screen` и `cloud.judge`, ошибка на прежние ключи, размер превью и `effort` ступени в запросах, оценке стоимости и ключах кэша; токены и время ступеней в отчёте.
- **Интеграционный тест** на тестовом альбоме Photos (~30 фото). Альбом содержит известные случаи: серию дублей, скриншот, смазанный кадр, Live Photo, кадры двух разных «тем». Тест проверяет FR-3–FR-6, NFR-1 и NFR-5.
- **Оценка качества** (NFR-3, NFR-4) — прогон на альбоме прошлой поездки с ручной оценкой пользователя.

## 11. Первый шаг реализации — spike

Цель — проверить предпосылки до основной разработки. Скрипт, обращающийся к Photos, запускает пользователь в своём Terminal (с доступом только к Photos); остальные проверки выполняются по скопированным файлам. На медиатеке пользователя (macOS 26, «Оптимизация хранилища») проверить:

1. PhotoKit через pyobjc из Terminal получает доступ Photos, находит альбом по имени и отдаёт по снимкам: дату, размеры, признаки Live/скриншот, ресурсы (основное фото, видеочасть).
2. Превью снимков, оригиналы которых в iCloud, получаются через PhotoKit; время на 1000 снимков.
3. Скачиваются из iCloud и записываются в файлы оригиналы и видеочасть Live Photo.
4. Через `pyobjc` работают эстетическая оценка Vision и визуальный отпечаток; подбираются пороги отсева мусора и дублей.
5. Первая ступень на `claude-haiku-5-5` по 5 запросам пользователя: полнота и точность отбора на ~200 превью, расход токенов и время на тему.
6. По результатам выбираются значения по умолчанию `candidates_per_theme`, `preview_long_side_px` (с версии 0.5.1 — `cloud.screen.preview_px` и `cloud.judge.preview_px`), `group_size`.

**Критерий провала:** не выполняется пункт 1 или 3. Тогда модуль `library` переводится на Swift-хелпер с PhotoKit (решение D1), остальное не меняется.

## 12. Выбор прод-модели

Выполняется после отладки, когда конвейер и промпты стабилизированы на `claude-haiku-5-5` и в режиме без облака. Выбирается модель **второй** ступени; первая остаётся на Haiku 5.5, если прогоны не покажут, что она пропускает подходящие кадры.

1. Взять альбом прошлой поездки и 2–3 темы разного типа: по содержанию, по интервалу, смешанную.
2. Прогнать их с кандидатами в прод-модели второй ступени: `claude-haiku-5-5`, `claude-sonnet-5-5`, `claude-opus-5-5`.
3. Пользователь сравнивает `report.md` прогонов по качеству (NFR-3) и стоимости (NFR-2). Время (NFR-4) учитывается третьим, по приоритету «качество > время > цена».
4. Победившая модель и подобранный для неё `effort` фиксируются в `cloud.judge.model` и `cloud.judge.effort`. По тем же прогонам калибруется вес соответствия стилю страницы (FR-11.4).

## 14. Принятые риски

| Риск | Последствие | Как смягчаем |
|---|---|---|
| PhotoKit через pyobjc: асинхронные вызовы с обработчиками неудобны в Python | Сложнее код адаптера, возможны зависания на загрузке из iCloud | Spike (§11); таймауты на загрузку; запасной путь — Swift-хелпер |
| Первая ступень пропускает подходящие кадры (в spike Haiku и Sonnet расходились на ~10% кадров) | Неполные посты по теме | Мягкий порог `min_theme_relevance` = 5, вторая ступень перепроверяет соответствие; в отчёте видно, сколько кадров признано подходящими; в теме можно задать интервал |
| Неоднозначная формулировка темы («GEM», «Карнакский музей») или близкие по смыслу темы (маска Тутанхамуна в GEM и Долина Царей) | Кадры уходят не в ту тему | Подсказки по формулировкам (FR-1.2, README); кадр может относиться к нескольким темам (FR-1.5); проверка на приёмке (Task 13) |
| Лимит скорости API (500 000 входных токенов в минуту на Haiku 5.5) | Первая ступень не быстрее ~2 минут на 1000 снимков, ответы 429 | Ограничение параллельности, ожидание и повтор при 429, сохранение каждой обработанной группы в кэш |
| Превью почти всех снимков уходят в Claude API | Фото поездки покидают Mac в уменьшенном виде | Принято пользователем при выборе D2 |
| Оценки модели в разных группах откалиброваны неидеально | Ранжирование между группами неточное | Общая рубрика, распределение групп по черновой оценке, при равенстве — локальная оценка |

| Загрузка превью и оригиналов из iCloud медленная | Превышение NFR-4 | Замер в spike; оригиналы загружаются только для каруселей, запасных и stories |
