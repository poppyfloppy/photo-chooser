## Окружение

- **Запускать только из Terminal.app.** В панели Terminal приложения Claude (и через `!` в чате) photo-chooser молча падает с кодом 134: у процесса Claude нет доступа к Photos.
- **Ключ API — в Keychain** (FR-13), запись `anthropic-api-key`. Проверка — `uv run photo-chooser key status`, заменить ключ — `key set`.
- **Кэш оценок и журнал расходов альбома** (`~/Library/Caches/photo-chooser/`) у каждого компьютера свой.
  - В 0.5.1 версии промптов сменились (`judge-8`, `compose-6`), к ключам кэша добавились `effort` и размер превью. Поэтому старые ответы не подходят: первый прогон на любом компьютере заново посчитает вторую ступень и сборку по полной цене. Первая ступень пересчитается тоже: её ключ теперь `screen-4/medium/1024px`.
  - Бюджет по альбому уже выше лимита по умолчанию ($5): на первом Mac было накоплено $18.27, на втором — $7.95. Поэтому прогонам нужен `--max-cost`. Точную цифру подсказывает `--dry-run`.
- **Конфиг — новый формат с версии 0.5.1** (D18). На обоих Mac в `~/.config/photo-chooser/config.yaml` ещё старые ключи `cloud.model` и `cloud.effort`. Первый запуск выдаст ошибку с готовым фрагментом, замени ключи по нему. Целевой вид:

```yaml

  judge: {model: claude-opus-5-5}   # вторая ступень и сборка; effort high и 768 px — по умолчанию
style:
  albums: [Snapseed, Instasize]        # опубликованные посты
  screenshots_album: Instagram style   # первые 2 — гриды ленты, следующие 2 — stories
```

### Сценарии пользователя (со схемы)

1. **Задать стиль.** Модель пишет стиль постов (текст и N референсных изображений) и стиль историй (то же).
2. **Получить выборку по альбому:**
   1. пользователь создаёт или выбирает альбом с фото и указывает часовой пояс;
   2. задаёт темы: название, тэги (необязательно), даты from–to (необязательно), пост и/или истории (по умолчанию и то, и другое); обязательно что-то одно из тэгов и дат;
   3. приложение отбирает фото и предлагает карусель поста с альтернативами и истории;
   4. пользователь подтверждает или заменяет кадры из альтернатив и историй, финализирует пост и истории — цель: попадание 80 %+, остальное пользователь доводит сам;
   5. пользователь ретуширует выбранные кадры в своём редакторе;
   6. модель оценивает кадры после ретуши и даёт рекомендации по стилю и референсам;
   7. пользователь публикует пост в Instagram сам.

### Целевая архитектура

- **Ядро на Python** — сервис-монолит с конфигами. Внутри: фасад (HTTP API), прикладная логика, очередь заданий, порт LLM-провайдеров, порт БД, хранилище секретов.
- **Клиенты:**
  - **macOS** (SwiftUI multiplatform, PhotoKit) — первым: приложение для себя проще распространить;
  - **iOS** — полный, но позже;
  - **CLI** остаётся клиентом фасада.
- **iCloud Photos** — канал между устройствами: снимки и ретушь синхронизирует Photos.
- **Хостинг** — пока ядро на ноутбуке пользователя.

### Договорённости

1. **Ядро не читает Photos и не запускает Vision.**
   - Клиент читает снимки через PhotoKit, считает локальные признаки через Vision (эстетика, мусор, дубли), уменьшает превью и шлёт ядру превью и признаки.
   - Ядро общается с LLM.
   - CLI тоже становится таким клиентом: чтение Photos и Vision из ядра переезжают в него. Это первый клиент, на котором проверяется API, ещё до GUI.
2. **Фасад** — HTTP и JSON, асинхронный: «создать запуск → ход → результат». Ход запуска идёт потоком событий (SSE). API описан в OpenAPI, Swift-клиент генерируется из него.
3. **API проектируется заново** вокруг сущностей сценариев: альбом, тема, стиль, запуск, предложение постов, решения пользователя, оценка после ретуши. Детали спрятаны за интерфейсами. Нынешние команды CLI (`run`, `style`, `key`) наружу как есть не выставляются.
4. **Очередь — в ядре**, два уровня:
   - задания «запуск по альбому» лежат в БД и переживают перезапуск ядра и отключение клиента;
   - внутри задания — пул запросов к LLM с лимитом параллельности и повторами (сейчас это `SyncTransport`).
5. **Порт LLM — универсальный, на уровне предметной области:** оценить группу кадров по теме, собрать посты, написать стиль, оценить кадр после ретуши.
   - Смена вендора — новая реализация порта и переключение в конфиге ступени (провайдер и модель).
   - Модель без картинок на входе реализацию не получает, флагов возможностей нет.
   - Кэш префикса, `effort`, структурированный ответ — внутри адаптера Anthropic. Пример будущего вендора на схеме — DeepSeek.
   - В ключ кэша результатов добавляется провайдер.
6. **БД** — SQLite за адаптером. Пользователь пока один: без владельцев в таблицах и без регистрации. Если понадобится — новая схема и миграция.
7. **Секреты:**
   - ключ LLM есть только у ядра: порт `SecretStore`, на Mac — Keychain (уже есть), на сервере — менеджер секретов платформы; клиенты ключа не видят;
   - доступ клиентов к фасаду — токен устройства, выданный при привязке и хранимый в Keychain устройства; ядро хранит только хэши токенов и может отозвать устройство;
   - страховка — лимит расходов на ключ в консоли Anthropic.
8. **Тема.**
   - Тэги — это нынешний `query`: в промпт уходят склеенными в текст.
   - Ключ темы — sha256 канонического JSON структуры: название, тэги как множество (без пробелов по краям, в одном регистре, без повторов, отсортированы), даты.
   - Текст промпта собирается из той же канонической формы.
   - Переключатель «пост и/или истории» в ключ темы не входит: он меняет лимиты сборки, а они уже в отпечатке входа сборки.
9. **Превью хранятся на ядре:**
   - **ключ превью** — sha256 байтов JPEG. При запуске клиент шлёт манифест альбома: идентификатор снимка и хэш превью. Ядро отвечает, каких хэшей нет, клиент досылает только их;
   - клиент кэширует хэш вместе с `modificationDate` снимка: изменилась дата — превью строится заново, хэш выходит прежним, если картинка не менялась;
   - **размер** — ядро хранит превью первой ступени (1024 px), меньшие размеры получаются из него. Если первую ступень увеличат, превью загружаются заново;
   - **удаление** — превью живёт, пока на него ссылается хоть один альбом (ссылки обновляются с манифестом). Без ссылок оно удаляется через 30 дней, при удалении альбома в приложении — сразу. Лимита на объём пока нет: ~1000 снимков — порядка 200 МБ.
10. **Что инвалидирует результаты модели:**
    - **отбор** (первая и вторая ступени, сборка) — по идентификатору снимка. Ретушь его не сбрасывает: вторая ступень и так оценивает кадр с учётом обработки, а иначе каждая правка в Photos или новое кодирование JPEG после обновления macOS стоили бы денег;
    - **оценка после ретуши** — по хэшу превью;
    - **локальные признаки** — по хэшу превью;
    - остальные части ключа как сейчас: провайдер, модель, версия промпта, `effort`, размер превью, стиль, тема.
11. **Оценка после ретуши** — это ступень judge с другим промптом: тот же порт, тот же стиль и референсы, на вход — отретушированный кадр.

### Связка ключей: превью на ядре ↔ снимок на Mac ↔ снимок на iPhone

| Где | Идентификатор | Как получить |
|---|---|---|
| Photos на Mac | `PHAsset.localIdentifier` — свой на этом Mac | PhotoKit |
| Photos на iPhone | `PHAsset.localIdentifier` — свой на этом iPhone | PhotoKit |
| Общий для устройств | `PHCloudIdentifier.stringValue` — один у снимка на всех устройствах одной медиатеки iCloud Photos | `PHPhotoLibrary.cloudIdentifierMappings(forLocalIdentifiers:)`, обратно — `localIdentifierMappings(for:)`; macOS 12+, iOS 15+ |
| Ядро | снимок = `PHCloudIdentifier`; превью = sha256 байтов; связь «снимок → текущий хэш превью» | манифест клиента |

- Перевод `localIdentifier ↔ PHCloudIdentifier` делает клиент на своей стороне. Ядро `localIdentifier` не знает.
- Результаты отбора привязаны к `PHCloudIdentifier`; оценка после ретуши и локальные признаки — к хэшу превью.
- Условие: iCloud Photos включены на обоих устройствах под одним Apple ID. Снимок, ещё не выгруженный в iCloud, `PHCloudIdentifier` не имеет: клиент его пропускает и сообщает об этом.
- CLI на Mac тоже шлёт `PHCloudIdentifier`: через PyObjC доступен тот же API.
- Сейчас кэш ключуется полным `localIdentifier` Mac (`library/photokit_library.py`). Чтобы не платить заново, его нужно один раз перевести на `PHCloudIdentifier` тем же API.

### Отложенные мелочи

- **Из ревью 0.5.1:**
  - подсказка ценового порога пишет «preview_px ступени» и не называет ключ (`judge/stages.py`), подсказка сборки не упоминает `cloud.judge.preview_px`;
  - в `judge/transport.py` остались два комментария про пакеты (FR-12);
  - подсказки типов в `select.py` описывают пары вместо троек, лишние пустые строки в `cache.py` и `report.py`;
  - у раннеров `preview_px` имеет значение по умолчанию — второй источник размера превью рядом с функцией `preview`;
  - конфиг и с `cloud.batch`, и с плоскими ключами даёт две ошибки по очереди;
  - тест неверного `effort` пишет старый `cloud.effort` и падает на ошибке прежних ключей, а не на неверном значении;
  - кэш локальных признаков не зависит от размера превью — закрывается договорённостью 10;
  - тесты CLI пишут трассировку в настоящий `~/Library/Logs/photo-chooser`.
- **Из прежних версий:**
  - `posts.carousels: 0` теряет лучшие кадры;
  - `ValueError` ценового порога сборки роняет запуск;

  - если первая карусель не скачалась целиком, номера в отчёте и папках расходятся;
  - нет теста на ранг резкости в причине для `--no-cloud`;
  - ошибка устаревшего ключа конфига не называет файл;
  - на приёмке 0.3 выгрузка stories «Гизы» зависла на ~4 минуты без вывода (первый stories — кадр из Live Photo), причина не выяснялась;
  - `key set` не разбирает аккаунт записи вида `<NULL>` и может создать вторую запись;
  - устаревший docstring `pipeline.py`; `stages.py` импортирует приватный `_quiet` из `transport.py`.
